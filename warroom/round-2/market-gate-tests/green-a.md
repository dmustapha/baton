# GREEN Pressure Test: Exit Relay

## Verdict

**KILL at Gate 0: Market Reality, independently reinforced by Gate 0b: End-to-End Operability. Do not score or select as a finalist.**

Exit Relay's attractive implementation facts do not repair its missing market foundation. The proposed buyer and workflow depend on a hypothetical private FXRP router that is not shown to exist as a current buyer, operator role, repeated asset flow, or reachable distribution channel. Native FAssets redemption requests are FIFO-assigned and `RedemptionRequested` data is public, so the claimed naturally private request-inclusion problem does not match the demonstrated native workflow. Native redemption default and compensation already address non-payment, making the project's capacity-reduction overlay a substitute for an existing protocol safeguard rather than evidence of an unserved current job.

## Gate application

### Gate 0: Market Reality — FAIL

1. **Primary evidence — FAIL.** No current primary evidence establishes that an existing buyer operates a private FXRP redemption router, receives hidden service requests, or suffers selective omission from such a queue. A constructed application workflow is not demand evidence.
2. **Named buyer — FAIL.** “Private FXRP router” is a project-created role, not an identified existing organization or established operator role with authority and reason to adopt.
3. **Economic behavior — FAIL.** Live FXRP transfers prove that tokens can move through the project contract. They do not prove existing spend, fees, repeated routing behavior, or willingness to fund this private-capacity service.
4. **Current substitute — FAIL.** Native FAssets uses FIFO assignment and public redemption-request state; native default/compensation already handles non-payment. The proposal neither proves a gap in those mechanisms nor explains why a buyer would replace or layer over them.
5. **Natural privacy — FAIL.** The mechanism treats request inclusion and queue membership as hidden, but the relevant native redemption request is public. Confidentiality is manufactured by moving the job into a hypothetical private router rather than inherited from the existing workflow.
6. **Plain-language acceptance — FAIL.** Without first explaining the invented private router, a normal FXRP redeemer is unlikely to recognize “prove my hidden request was included so the provider's next private cap shrinks” as their current problem. Their recognizable problem is non-payment, for which native compensation already exists.
7. **Reachable first users — FAIL.** No existing channel to five operators of this routing model is established. Acquiring users requires first creating or persuading adoption of the new intermediary role.

Gate 0 is all-or-nothing. Any one failure kills the idea; Exit Relay fails all seven items.

### Gate 0b: End-to-End Operability — FAIL

| Load-bearing transition | Authority/interface finding | Result |
|---|---|---|
| Receive hidden native redemption requests into a private service batch | Native requests are FIFO-assigned and public; no existing private-router actor or exact source/interface is established | FAIL |
| Decide the provider's next redemption capacity | The project can update only its own router cap; it has no authority to change native FAssets assignment or agent capacity | FAIL |
| Interpret partial/non-payment as an unhandled condition | Native default/compensation already owns the protocol response; no demonstrated authority chain makes the overlay necessary | FAIL |
| Transfer or reroute project-held FXRP | A live `transfer` receipt can prove this project-owned state change only | PASS, but insufficient |
| Deliver the rerouted tranche through a real fallback redemption workflow | No existing fallback actor, exact callable integration, settlement source, or adoption path is established | FAIL |

The skill is explicit: a callable token transfer proves only that transfer. It cannot stand in for a real upstream buyer, private queue, protocol assignment right, provider-capacity control, fallback service, or adoption path.

### Later gates do not rescue it

- **Gate 1 relevance:** likely relevant to the event, but relevance cannot compensate for Gate 0.
- **Gate 2 buildability:** the project-owned router and polished 90-second demo may be buildable before the deadline, but the skill permits relaxation only of buildability when zero ideas survive. It does not permit relaxing market reality.
- **Gate 3 sponsor fit:** live FXRP movement and confidential inclusion computation are technically strong and independently load-bearing inside the invented application. Sponsor fit does not establish a buyer or valid native workflow.
- **Gate 5 demo:** the 8/10 visual cap-drop and reroute moment is persuasive theater, but demonstrates project-owned state, not market validity or native protocol authority.
- **Gate 6 ecosystem-native:** the framing is not grounded in the actual native flow. Public FIFO redemption requests undercut the hidden-inclusion premise, and native default compensation undercuts the claimed unmet non-payment outcome. The application router is an added market layer rather than an evidenced chain-native user job.

## Tempting rationalizations rejected

1. **“The deadline is near, so preserve the most buildable finalist.”** Rejected. Time pressure can narrow implementation scope; it cannot waive Gate 0 or invent demand.
2. **“It has live FXRP receipts, therefore the integration is real end to end.”** Rejected. Those receipts prove only project-controlled token movement, not upstream private demand, native assignment, provider authority, fallback fulfillment, or adoption.
3. **“Both sponsor tracks are deeply coupled, so market uncertainty is acceptable.”** Rejected. Track depth is evaluated only after Market Reality. Two load-bearing technologies can still form a product nobody currently needs.
4. **“The 8/10 demo hook will carry judging.”** Rejected. A surprising cap change can mask that the cap is self-created and has no authority over FAssets protocol capacity.
5. **“Private batch inclusion is novel enough to justify a new router market.”** Rejected. Novelty is a constraint on top of grounding, not a substitute for an existing buyer, workflow, economic signal, and natural private data.
6. **“Native compensation is slow or imperfect, so an overlay must help.”** Rejected. No supplied primary evidence demonstrates that gap, its cost, or a buyer willing to route assets through this substitute.
7. **“Public redemption data can be re-hidden inside the application.”** Rejected. The revised gate forbids circular hiding of already-public ledger data to manufacture Confidential Compute necessity.
8. **“Rejecting it leaves zero finalists, so the gates should bend.”** Rejected. The zero-survivor rule allows relaxing Gate 2 only. If the pool fails ecosystem grounding, the required response is to re-seed from native problems and market evidence, not promote a Gate 0 failure.

## Required pipeline consequence

Record Exit Relay as killed for **fictional buyer/workflow, invented privacy, duplicated native substitute, and incomplete authority chain**. If this leaves zero finalists, re-run generation from evidenced FAssets-native users, current workflows, economic behavior, and reachable channels. Do not relax Market Reality, End-to-End Operability, or Ecosystem-Native gates.
