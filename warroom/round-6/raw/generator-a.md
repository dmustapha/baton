# Round 6 — Generator A

## 1. GainLock

- **Name:** GainLock
- **Problem:** An FXRP holder can earn in a vault, but harvesting usually forces a vague choice between leaving everything exposed and withdrawing principal together with profit.
- **Market Anchor:** Current FXRP holders already deposit, hold vault shares, withdraw, and swap; active deployment and repeated DeFi transactions prove the behavior, while manual transaction sequences are the substitute.
- **Named Buyer:** A self-custodied FXRP holder using a yield-bearing ERC-4626-style vault.
- **Existing Workflow:** The holder approves FXRP, calls `IERC4626.deposit()`, watches share value, manually calculates profit, calls `redeem()`, then optionally swaps the proceeds.
- **Current Substitute:** Vault UI balances, wallet portfolio views, spreadsheets, and a manual full-or-partial withdrawal followed by a swap.
- **Mechanism:** The holder commits an FXRP principal floor and a minimum harvest lot. The state machine moves `Armed -> Compounding -> GainAvailable -> Crystallized -> Compounding`: `convertToAssets()` determines current FXRP value, `redeem()` can release only shares representing value above the floor, and a verified AMM router `exactInput` call converts only that realized gain into the holder's chosen output asset. If value is at or below the floor it enters `FloorLocked`, where no keeper can move FXRP; only the holder can lower the floor or exit. Each crystallization resets the share checkpoint without silently ratcheting principal down.
- **Chain-Native Angle:** The useful output exists because bridged XRP becomes programmable FXRP that can accrue value inside a Flare application and be split by onchain state into protected principal and spendable gain; the same XRP could not execute this state machine on XRPL alone.
- **Sponsor Fit:** FAssets/FXRP is the load-bearing asset, a live Flare vault and AMM are the applications, FTSOv2 supplies an optional minimum-output sanity bound, and Contract Registry resolves mutable protocol addresses where applicable. It targets only Interoperable Asset Products.
- **Demo Hook:** Deposit 100 FXRP, simulate visible vault gain, press “crystallize,” and show exactly 3 FXRP of gain become the chosen asset while the 100-FXRP floor remains deployed; then force a below-floor quote and show the same call fail closed.
- **Competitor-Derived Insight:** Existing flows prove FXRP acquisition and DeFi use, but useful composition needs a complete live-value action rather than another balance or lifecycle display.
- **Missing Outcome:** A holder-readable economic promise—“only realized gain may leave this position”—enforced across vault withdrawal and exchange.
- **Multi-Track Architecture (single-track):** One deep Interoperable Asset Products path: FXRP vault shares -> surplus-only redemption -> application-level swap -> holder-owned output. No confidential-compute claim.
- **Per-Track Load-Bearing Test:** Remove FXRP programmability or either `IERC4626.redeem()`/AMM `exactInput`, and GainLock cannot separate and realize cross-application gain; it collapses into manual accounting rather than the same product.
- **Proof Path:** FXRP approval and deposit event -> vault share/value reads -> surplus calculation -> exact share redemption event -> AMM swap event -> before/after FXRP floor and output balances -> replayable receipt; a no-surplus transaction demonstrates the safeguard.
- **Authority and Integration Map:** The holder alone approves FXRP, sets or changes the floor, selects the verified vault/router and receives output. The contract may be invoked by the holder or a permissionless keeper, but can call only the preauthorized `deposit()`, `redeem()`, and `exactInput` path within stored bounds. Vault and router contracts execute; public events and balance reads let the holder and judge verify. No agent, treasury, or project-funded transfer is assumed.
- **Adaptation Note:** Remixes self-authorized asset composition with forced reauthorization and before/after ownership proof: the unusual primitive is a profit-only permission boundary, not a generic auto-compounder or vault wrapper.

## 2. FXRP Thermostat

- **Name:** FXRP Thermostat
- **Problem:** An FXRP holder who supplies assets to a lending application has no simple way to reduce exposure gradually when XRP becomes turbulent without repeatedly guessing, withdrawing everything, and later changing their mind.
- **Market Anchor:** FXRP holders already lend, withdraw, hold liquid FXRP, and redeem; repeated asset use and protocol fees are the economic signal, while application UIs and manual sequences are the substitute.
- **Named Buyer:** A self-custodied FXRP holder supplying a verified Flare lending market.
- **Existing Workflow:** The holder calls the market's `supply(asset, amount, onBehalfOf, referralCode)`-category interface, watches XRP conditions elsewhere, and manually calls `withdraw(asset, amount, to)` before deciding whether to resupply or redeem.
- **Current Substitute:** Price alerts plus discretionary lending withdrawals, or keeping all FXRP idle from the start.
- **Mechanism:** The holder sets a maximum deployed amount, liquid reserve target, bounded step size, and two distinct FTSOv2 volatility thresholds. The state machine moves `Deployed -> Braking -> Reserved` when observed range crosses the high threshold, withdrawing only one authorized step per epoch; it moves `Reserved -> Reentering -> Deployed` only after the low threshold holds for a full cooldown. Hysteresis and a one-step epoch cap prevent churn. At every `Reserved` state the holder can permanently mark a slice `ExitOnly`, after which no automation may resupply it and the holder may send it through the current Asset Manager redemption interface.
- **Chain-Native Angle:** FTSOv2 changes the allowed state of programmable FXRP inside a Flare lending application, while the terminal `ExitOnly` state reconnects that reserve to XRP through FAssets redemption; this is an interoperable risk posture, not a price dashboard.
- **Sponsor Fit:** FXRP, FTSOv2, a verified lending `supply/withdraw` interface, the published FAssets redemption interface, and Contract Registry address resolution are used in one asset lifecycle. It targets only Interoperable Asset Products.
- **Demo Hook:** Start fully supplied, push the displayed FTSOv2 range through the high threshold, execute one bounded withdrawal into liquid FXRP, prove a second same-epoch withdrawal is refused, then mark that slice `ExitOnly` and initiate its XRP redemption.
- **Competitor-Derived Insight:** Delayed finality and fragmented application states matter, but a compelling product must turn verified state into a bounded holder-authorized economic consequence.
- **Missing Outcome:** A memorable, reversible-until-exit “risk thermostat” that changes how much FXRP is earning versus redemption-ready without handing open-ended authority to an operator.
- **Multi-Track Architecture (single-track):** One Interoperable Asset Products lifecycle: lending-supplied FXRP <-> holder reserve -> one-way redemption slice. FTSOv2 controls bounded transitions but does not create a second track claim.
- **Per-Track Load-Bearing Test:** Remove FTSOv2 and the hysteretic state transitions have no decentralized trigger; remove FXRP lending or FAssets redemption and the thermostat no longer changes a connected asset's economic use and exit posture.
- **Proof Path:** Supply event -> FTSOv2 round/value identifiers -> epoch transition -> exact lending withdrawal event -> reserve balance -> same-epoch refusal -> holder `ExitOnly` signature -> Asset Manager redemption event and eventual FDC-backed XRP payment proof.
- **Authority and Integration Map:** The holder funds FXRP, approves a capped amount, chooses thresholds, can pause, marks `ExitOnly`, and receives redeemed XRP. A permissionless caller may advance an eligible epoch but cannot change thresholds, recipient, amount cap, or reenter an exit-only slice. FTSOv2 supplies public observations; the lending market and Asset Manager execute exact published calls; FDC verifies the final external payment.
- **Adaptation Note:** Combines negative-evidence-style fail-closed action with a thermostat's hysteresis and forced expiry: unlike familiar stop-loss automation, it moves in capped reversible steps and makes the final cross-chain exit an explicit, holder-only state transition.

## 3. Redemption Battery

- **Name:** Redemption Battery
- **Problem:** A current FXRP holder may want to keep principal productive yet lacks a natural way to turn small, irregular DeFi gains into a coherent XRP exit without repeatedly dismantling the core position.
- **Market Anchor:** FXRP holders already hold vault shares, claim or realize gains, and redeem FXRP to XRP; vault value, redemption fees, and repeated lifecycle activity are existing economic signals.
- **Named Buyer:** A self-custodied FXRP holder with FXRP in a yield-bearing ERC-4626-style application.
- **Existing Workflow:** The holder checks vault value, manually redeems a small number of shares, waits until the amount seems worth redeeming, then creates a separate FAssets redemption request.
- **Current Substitute:** Leave small gains invested indefinitely, withdraw principal with gain, or keep an offchain note until a manually chosen redemption amount accumulates.
- **Mechanism:** The holder fixes a principal floor, charge threshold, and XRP recipient. The machine moves `Compounding -> Charging` as realized value above the floor becomes withdrawable, then calls `IERC4626.redeem()` only for that surplus into an isolated FXRP charge balance. Below the live Asset Manager minimum it cannot redeem. At the threshold it becomes `Charged`; only the holder can sign `Discharge`, which calls the published FAssets redemption interface for the exact battery balance and moves `Redeeming -> Paid` on proven XRP payment. The principal position continues compounding throughout, and the next charge cycle requires fresh holder authorization if recipient or limits change.
- **Chain-Native Angle:** The product converts application-produced FXRP surplus into discrete, protocol-valid XRP redemption lots. Its visible economic state is measured in both vault-backed FXRP gain and externally paid XRP, so the FAssets boundary is the product rather than decoration.
- **Sponsor Fit:** FAssets/FXRP, a verified `IERC4626.convertToAssets()/redeem()` application, current Asset Manager redemption parameters resolved through Contract Registry, and FDC payment proof form the full loop. It targets only Interoperable Asset Products.
- **Demo Hook:** Show a battery at 80%, add vault gain, call charge to cross 100% without touching the principal floor, then let the holder discharge and reveal the proven XRP payment; a below-minimum discharge visibly fails before any burn.
- **Competitor-Derived Insight:** Entry and redemption are possible today, but “FXRP became useful and produced an independently redeemable outcome” remains more persuasive than another mint/redeem progress screen.
- **Missing Outcome:** A holder-controlled unit of DeFi productivity that matures into real XRP while the earning principal stays deployed.
- **Multi-Track Architecture (single-track):** One Interoperable Asset Products state machine: vault yield in FXRP -> threshold-sized charge -> native FXRP redemption -> XRP receipt. No second-track dependency.
- **Per-Track Load-Bearing Test:** Remove vault surplus accounting and there is no battery charge; remove the native FAssets redemption call and the charged state never becomes externally paid XRP, destroying the defining outcome.
- **Proof Path:** Initial principal/share checkpoint -> `convertToAssets()` reading -> surplus-only `redeem()` event -> charged FXRP balance and current minimum check -> holder discharge signature -> Asset Manager redemption event -> FDC-attested XRP payment -> exact recipient receipt; below-minimum and below-floor calls prove safeguards.
- **Authority and Integration Map:** The holder supplies and approves FXRP, fixes the principal floor and XRP recipient, authorizes each discharge, and receives XRP. A caller can charge only verified surplus within the allowance; nobody else can discharge, change recipient, or consume principal. The vault executes redemption, Asset Manager assigns/executes native redemption, the assigned protocol agent pays as prescribed, and FDC verifies payment. No cooperating fictional actor is required.
- **Adaptation Note:** Remixes first-session countdown/reveal with participant economics and a proof-carrying receipt: gains “charge” a protocol-valid cross-chain action, producing a user-visible maturity mechanic rather than wrapping redemption or merely tracking it.

## 4. Earn-or-Exit Covenant

- **Name:** Earn-or-Exit Covenant
- **Problem:** FXRP holders often leave a DeFi position running by inertia even when it has failed the holder's own minimum productivity test, then face a separate manual decision about whether to return to XRP.
- **Market Anchor:** Current FXRP holders repeatedly deposit, withdraw, hold shares, and redeem; yield opportunity cost and mandatory redemption fees make the continue-versus-exit decision economically real.
- **Named Buyer:** A self-custodied FXRP holder evaluating whether an existing FXRP vault deserves another fixed holding epoch.
- **Existing Workflow:** The holder deposits via `IERC4626.deposit()`, periodically compares share value by hand, decides whether performance was acceptable, calls `redeem()`, and separately requests native redemption when leaving Flare.
- **Current Substitute:** Open-ended vault deposits, calendar reminders, spreadsheets, and discretionary withdrawals based on a UI APY.
- **Mechanism:** At entry the holder signs an epoch length, minimum net FXRP gain, principal floor, grace window, and XRP recipient. The machine moves `Committed -> Measured` at epoch end using actual `convertToAssets()` value, not advertised APY. If the hurdle is met it enters `Renewable`; the holder can claim gain and explicitly sign the next epoch. If the hurdle is missed it enters `ExitDue`; anyone may execute the preauthorized exact `redeem()` to liquid FXRP during the grace window, but only the holder can choose `RedeemToXRP` through Asset Manager or `Recommit` with new terms. If neither occurs, funds remain liquid and holder-owned—never silently recommitted.
- **Chain-Native Angle:** A Flare application position receives an enforceable service-level covenant whose terminal outcome can cross back to XRP through FAssets. Programmable FXRP makes “earn enough or become exit-ready” an asset state rather than a reminder.
- **Sponsor Fit:** FXRP is deposited in a verified ERC-4626-style application; FTSOv2 may normalize the hurdle for display but vault-denominated realized FXRP is authoritative; Asset Manager and FDC complete optional XRP redemption; Contract Registry resolves protocol addresses. It targets only Interoperable Asset Products.
- **Demo Hook:** Run two accelerated epochs side by side: one clears the hurdle and reveals a gain claim plus explicit renew button; the other misses, automatically exits the vault to liquid FXRP, refuses silent renewal, and lets the holder initiate XRP redemption.
- **Competitor-Derived Insight:** Working proof and rounded products beat protocol demos; the underused opportunity is to make application performance cause a complete asset transition, not merely report it.
- **Missing Outcome:** A holder-authored economic deadline that converts an underperforming FXRP position into controlled liquidity and offers—without forcing—a native XRP exit.
- **Multi-Track Architecture (single-track):** One Interoperable Asset Products path: committed FXRP vault epoch -> realized-performance branch -> gain claim and reauthorization, or liquid FXRP and optional native redemption.
- **Per-Track Load-Bearing Test:** Remove the callable vault interface and no realized performance or enforced exit exists; remove programmable FXRP/FAssets and the covenant cannot turn application underperformance into a connected-asset choice ending in XRP.
- **Proof Path:** Holder covenant signature -> FXRP deposit/share event -> start/end `convertToAssets()` checkpoints -> deterministic hurdle branch -> exact redeem or surplus claim event -> holder reauthorization or Asset Manager redemption -> FDC-backed XRP receipt; a missed-hurdle renewal attempt proves the fail-closed rule.
- **Authority and Integration Map:** The holder funds and approves FXRP, defines terms, receives all assets, and alone chooses recommitment or XRP redemption. A permissionless caller may settle an expired epoch only through the preauthorized `redeem()` amount and to the holder's contract balance. The vault executes deposit/redeem, Asset Manager handles holder-requested redemption, and FDC verifies external payment. No keeper may alter terms, redirect value, or invent protocol state.
- **Adaptation Note:** Combines forced expiry and reauthorization with live performance receipts and closed-loop action. The novelty is a holder-written productivity covenant whose failed epoch changes FXRP's economic state; it is neither a vault wrapper, alert, nor generic recovery flow.
