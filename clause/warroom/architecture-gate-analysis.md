# Architecture Gate Analysis — Flare Summer Signal

## Scope and evidence boundary

This is a strict Gate 3c/5/6 review of all 20 durably recorded raw ideas. It uses only the raw idea pool, active brief §11 Warroom guidance, `config.json`, and the generator-safe opportunity map. It does **not** use named competitors, saturation, prior projects, collision appendices, or differentiation evidence.

The deadline is 2026-08-14 19:59 UTC, leaving roughly one build day. A `PASS` here means the raw architecture is eligible for downstream synthesis/scoring; it is not permission to claim an integration as live. Any pass must still prove the named Flare calls immediately.

## Hard-gate interpretation

An idea passes only when all seven statements are credible at once:

1. **Interoperable primitive:** a real FXRP/FAssets transition, Smart Account authorization, PMW external action, or FDC-gated asset lifecycle—not a balance display, arbitrary ERC-20 transfer, or undefined “repair adapter.”
2. **Confidential primitive:** an actual FCC/FCE operation with private inputs, minimum disclosure, machine status, signed result, and onchain verification—not ordinary TypeScript/backend secrecy.
3. **Independent removal:** removing either primitive destroys a necessary outcome or guarantee.
4. **Joined causality:** one user trigger reaches external/FAsset state, confidential execution, verified result, asset consequence, and exact receipt.
5. **Demo compression:** the causal path and one negative safeguard fit a 90-second judge demo.
6. **Remaining-time scope:** one builder can prove the riskiest live integration and finish the thin product before the deadline.
7. **Ecosystem nativeness:** the costly failure arises from Flare/XRPL/FAssets, transparent-ledger behavior, cross-chain proof, Smart Account/PMW authority, or FCC machine lifecycle. Merely paying a generic workflow in FXRP fails.

FCC operational honesty is necessary but not sufficient. Correctly labeling a fixture prevents overclaiming; it does not turn a fixture-backed core bounty primitive into a pass.

## Decision summary

- **Pass: 4** — Quiet Exit Window, Exit Envelope, Mandate Zero, SplitLock.
- **Kill: 16** — all exact causes are below.
- The four passes still carry proof-before-build stop conditions. Failure to prove the stated live Smart Account/PMW/FCC path converts the pass to a kill; a mock cannot substitute for the load-bearing track primitive.

## Generator A

### A1 — Late Route: KILL

- **Track primitives:** FCC private disposition is distinct and necessary, but the interoperable side assumes the app can intercept a late direct mint, place resulting FXRP into its own quarantine vault, and later deliver or refund it. No protocol-valid hook or controlled pre-mint custody path is identified.
- **Removal/joined path:** logically sound only after that unsupported quarantine transition exists; without it, FCC classifies a payment but cannot control the minted asset.
- **Demo/scope:** the red-to-green demo is excellent, but proving direct mint, late-payment FDC evidence, quarantine custody, and FCC in one day is not credible. The proposed fixture fallback would simulate the load-bearing Interoperable Asset primitive.
- **Nativeness/FCC honesty:** strongly Flare-native and honest about machine status, but honesty does not repair the missing executable asset transition.
- **Exact kill cause:** **undefined control over the real late-mint asset state; the core rescue becomes fixture-backed if that assumption fails.**

### A2 — Veiled Change Order: KILL

- **Track primitives:** real FXRP escrow/Smart Account release and FCC private entitlement are distinct, independently necessary, causally joined, and demoable.
- **Demo/scope:** one vault, one bounded authorization, and an over-amount refusal fit 90 seconds and are reasonably scoped.
- **Nativeness:** the costly problem is a conventional freelance invoice dispute. The product remains intact if FXRP/Smart Accounts are replaced by any ERC-20 and account-abstraction wallet; Flare does not create the failure.
- **FCC honesty:** the trust boundary is explicit, but the evaluator is still only a deterministic document rules engine unless deployed as a real FCC/FCE operation.
- **Exact kill cause:** **generic commercial escrow with Flare as settlement plumbing, failing the ecosystem-native gate.**

### A3 — Payroll Pulse: KILL

- **Track primitives:** PMW external payroll and FCC private failover policy are distinct and pass both removal tests; the joined receipt is coherent.
- **Demo/scope:** two confidential machines, heartbeat/liveness logic, signer rotation, PMW batch creation, XRPL broadcasts, and Flare reconciliation exceed the remaining one-builder window. Local PMW/FCC emulation would remove both bounty proofs.
- **Nativeness:** signer continuity is relevant, but payroll is a generic real-world wrapper and dominates the user story.
- **FCC honesty:** simulation labels are honest; the core still requires a real FCC lifecycle and replacement-machine identity transition, not two local workers.
- **Exact kill cause:** **too many live infrastructure dependencies for the remaining time, with a generic payroll surface and mock-only fallback.**

### A4 — Kinship Window: KILL

- **Track primitives:** FDC activity plus FXRP vault release and FCC beneficiary resolution are conceptually distinct; each removal breaks the intended guarantee.
- **Joined path:** the path depends on a reliable, bounded FDC non-activity/inactivity fact across a meaningful interval. The idea does not specify a protocol-supported nonexistence query or challenge evidence sufficient to distinguish lost access from ordinary silence.
- **Demo/scope:** time acceleration and inactivity fixtures can show a state machine, but not the load-bearing external evidence within 90 seconds or the remaining build day.
- **Nativeness:** cross-chain inactivity adds a native trigger, yet the dominant product is generic inheritance and includes an implicit legal/identity adjudication surface.
- **Exact kill cause:** **unproven inactivity/nonexistence primitive plus a fixture-driven long-duration lifecycle and generic inheritance core.**

## Generator B

### B1 — Redemption Rewind: KILL

- **Track primitives:** FCC counterfactual recovery is distinct and necessary. FDC can prove payment/non-payment, but “retry, challenge, or release” is not one named protocol-valid FAssets transition that the proposed vault controls.
- **Removal/joined path:** the removal tests are logically correct; the joined path stops at the undefined exception adapter.
- **Demo/scope:** partial redemption, three confidential branches, FDC, FCC, and real correction are too broad for one day unless the recovery leg is already available. The stated fixture fallback would simulate the central asset recovery.
- **Nativeness/FCC honesty:** highly ecosystem-native and honestly labeled, but not executable as written.
- **Exact kill cause:** **the asset-side recovery verb is underspecified and may not be callable by the application, making the final economic action non-provable.**

### B2 — Second Look Credit: KILL

- **Track primitives:** FCC rescoring and a Smart Account amendment are distinct on paper, but no live credit position or protocol term exists for the adapter to amend; a collateral lock/release in a bespoke vault is not evidence of an actual credit-line change.
- **Removal/joined path:** causality is complete only inside a newly invented lending system, which expands scope beyond the thin appeal mechanic.
- **Demo/scope:** the single-use capsule is visually concise, but building even a credible minimal credit lifecycle, policy versions, Smart Account adapter, FDC evidence, and FCC is not one-day work.
- **Nativeness:** underwriting appeal is conventional credit; it survives unchanged on another EVM chain.
- **Exact kill cause:** **generic credit workflow plus no existing economic term for the claimed amendment to change.**

### B3 — Machine Lifeboat: KILL

- **Track primitives:** PMW XRP rescue and FCC replacement-machine authorization are distinct, load-bearing, and causally joined; the removal tests are strong.
- **Demo/scope:** the raw design requires two FCC machine epochs, liveness evidence, an onchain continuity state machine, PMW broadcast, FDC reconciliation, and replay protection. That is not credible in the remaining build day.
- **Nativeness:** strongly native to FCC/PMW operations.
- **FCC honesty:** it clearly separates observed and simulated status, but its fallback explicitly fixtures the PMW asset leg. A local second signer is not proof of FCC machine rotation or attestation continuity.
- **Exact kill cause:** **operationally valid concept whose minimum honest live proof spans too many immature integrations for the remaining time.**

### B4 — Collateral Circuit Breaker: KILL

- **Track primitives:** private branch simulation is necessary, but “repay/redeem/unwind” again names three possible economic actions without selecting one actual callable FAssets path or a protocol position the app controls.
- **Removal/joined path:** strong abstractly; the path breaks at the unspecified vault/lifecycle adapter.
- **Demo/scope:** before/after buffer and abstention fit 90 seconds, yet the collateral market, oracle state, real position, and corrective transition would be simulated or newly built.
- **Nativeness:** FAssets liquidation risk is native enough; the failure is execution, not relevance.
- **FCC honesty:** scenarios are labeled, but a live signature over simulated collateral does not prove the Interoperable Asset track.
- **Exact kill cause:** **no concrete live FAssets position or single supported corrective action behind the claimed collateral rescue.**

## Generator C

### C1 — VeilCheck Escrow: KILL

- **Track primitives:** real FXRP escrow and FCC hidden-test evaluation are cleanly distinct, independently necessary, causally joined, small, and highly demoable.
- **Demo/scope:** this is among the most buildable raw architectures: one contract, one narrow worker, one split/refund path, one timeout safeguard.
- **Nativeness:** it is still generic software-delivery escrow. Any ERC-20 and any TEE-enabled EVM stack preserves the full product; Flare/XRPL/FAssets do not create the costly failure.
- **FCC honesty:** machine labels and onchain signature checks are excellent, but the worker must actually be an FCC/FCE extension rather than an ordinary TypeScript process.
- **Exact kill cause:** **fails ecosystem nativeness despite excellent two-track mechanics and scope.**

### C2 — Quiet Exit Window: PASS

- **Track primitives:** a one-use Smart Account authorization over real FXRP is a concrete interoperable action; FCC privately derives the unique cap, route hash, minimum return, expiry, or abstention. The primitives are distinct and each removal destroys the safe unwind.
- **Joined path:** owner policy and real FXRP state → private route simulation → signed envelope → Smart Account verification → one bounded FXRP movement/refusal → before/after receipt. The causality is direct.
- **Demo/scope:** execute, source-conflict abstain, and replay rejection fit 90 seconds. One policy module, one narrow worker, and one transfer adapter are feasible if the “unwind” is constrained to a real supported FXRP action rather than a mock swap.
- **Nativeness:** transparent exit size/urgency and least-authority Smart Account execution are chain-native problems; FCC changes whether the asset action can exist.
- **FCC honesty:** the design explicitly exposes evidence and machine status. **Stop condition:** prove a real FCC/FCE instruction-result-signature path and Smart Account authorization first; simulated attestation or liquidity may be labeled, but the FCC result and real FXRP action may not be mocked.
- **Pass basis:** **small, causal, independently load-bearing dual-track state machine with a strong negative-path demo.**

### C3 — Cipher Refund Relay: KILL

- **Track primitives:** FDC source payment, PMW refund, and FCC private adjudication are distinct and form a complete causal loop.
- **Demo/scope:** the 90-second refund is clear, but shipping FDC verification, FCC operation, PMW external signing/broadcast, XRPL confirmation, and nullifier logic in one day is not credible. Fixture FDC or simulated PMW removes the very Interoperable Asset proof.
- **Nativeness:** the cross-chain execution is native, but damaged-goods refunds are generic merchant support and do not arise because of Flare.
- **FCC honesty:** status disclosure is sound; dependency breadth remains fatal.
- **Exact kill cause:** **three live sponsor subsystems for a generic merchant-refund problem, with an invalid mock fallback for the load-bearing external action.**

### C4 — ProofHush Bounty: KILL

- **Track primitives:** FCC report evaluation can control FXRP release, but the external XRP deposit-to-FXRP-pool mapping is not defined; FDC proves funding and does not itself mint or capitalize the pool.
- **Removal/joined path:** the causal path has an unproven asset conversion between verified XRP funding and an FXRP payout pool.
- **Demo/scope:** private exploit reproduction, originality accumulator, FDC, FCC, pool funding, payout, and appeal are too broad. A deterministic fake vulnerability proves a fixture workflow, not a useful product integration.
- **Nativeness:** bug bounties are generic and the product survives on any confidential-compute chain.
- **Exact kill cause:** **undefined cross-chain funding conversion, excessive confidential-evaluation scope, and non-native bounty core.**

## Generator D

### D1 — Exit Envelope: PASS

- **Track primitives:** a real FXRP deposit/allocation/unwind and FCC-derived one-use minimum-return authorization are distinct. Removing FXRP removes recovery; removing FCC removes the hidden-policy authority and keeps the vault frozen.
- **Joined path:** route fault → private simulation → signed bounds → verifier → real FXRP unwind → rejected below-minimum route and before/after balance. The result causes the asset action.
- **Demo/scope:** one vault/verifier and two deterministic route outcomes fit the remaining time and 90 seconds, provided the shipped claim is “bounded FXRP recovery” rather than a fabricated production yield aggregator.
- **Nativeness:** transparent strategy/urgency and recovery of an FXRP allocation are chain-native; the confidential policy is pivotal.
- **FCC honesty:** simulation and machine labels are explicit. **Stop condition:** one actual supported FXRP deposit/unwind and a real FCC/FCE signed result must execute; only route failure/liquidity may be fixture-labeled.
- **Pass basis:** **the core outcome can be reduced to one real asset transition plus one confidential authorization without losing its value.**

### D2 — Mandate Zero: PASS

- **Track primitives:** Smart Account authority that deterministically decays to zero is a real asset-control primitive; FCC privately re-derives the only next-cycle cap. The two removal tests are exact and independent.
- **Joined path:** expired mandate blocks transfer → private constraints enter FCC → signed new cycle cap → Smart Account verifies → exact FXRP action → spent mandate and replay/over-cap refusal receipts.
- **Demo/scope:** the mechanic is the demo and fits comfortably in 90 seconds. One policy module, one verifier, one narrow transfer adapter, and deterministic policy code are the smallest credible architecture in the pool.
- **Nativeness:** the problem is stale autonomous authority over Flare Smart Account/FXRP, not generic budgeting; FCC is what restores bounded authority.
- **FCC honesty:** machine status and simulated time are separated. **Stop condition:** package the policy as a real FCC/FCE operation and prove actual Smart Account enforcement on Coston2; a locally signed backend result does not pass.
- **Pass basis:** **clearest independent dual-track causality, lowest contract count, strongest one-day scope, and exact negative proofs.**

### D3 — SplitLock: PASS — HIGH OPERATIONAL RISK

- **Track primitives:** PMW performs one real external XRP supplier payment; FCC privately computes the safe intersection of two committed policies. Each primitive is independently necessary and the result is contract-verifiable.
- **Joined path:** payment intent → conflicting private policies → signed intersection/abstention → verifier → PMW transaction → external hash, recipient balance, and 701/replay rejection. Causality is excellent.
- **Demo/scope:** two deterministic policies and one payment fit 90 seconds. The code surface is narrow, but PMW availability and its exact instruction path are a critical one-day risk.
- **Nativeness:** split-brain confidential policy controlling a Flare-managed external wallet is ecosystem-native; external settlement is the product outcome.
- **FCC honesty:** the trust boundary is explicit. **Stop condition:** prove real PMW access and the real FCC/FCE instruction-to-result lifecycle before any UI work. Local PMW/FCC emulation converts this pass to a kill.
- **Pass basis:** **deepest natural joining of Confidential Compute and external-asset execution, contingent on immediate live-access proof.**

### D4 — Repair Receipt: KILL

- **Track primitives:** FDC evidence and FCC bounded policy are distinct, but “retry, reroute, or return” is not one protocol-valid asset method. The executor's authority over a failed FAsset redemption is assumed rather than established.
- **Removal/joined path:** abstractly strong; concretely, the joined path terminates at an undefined repair adapter.
- **Demo/scope:** evidence freshness, failure capsule, FCC, FDC, FAssets correction, and three refusal branches are too broad unless the repair method already exists. Fixture fallback would mock the core asset lifecycle.
- **Nativeness/FCC honesty:** strongly native and honestly labeled, but operational feasibility fails.
- **Exact kill cause:** **no single callable FAssets repair transition; the proposal proves observability and authorization but not that the app may correct the protocol state.**

## Generator E

### E1 — TagBack: KILL

- **Track primitives:** FDC payment evidence and FCC claimant matching are distinct; a real reserve transfer is possible. However, the reserved FXRP is not shown to arise from or be locked by the mistagged XRP payment, so the proposed transfer can become an app-funded reimbursement rather than correction of that lifecycle.
- **Removal/joined path:** the receipt is visually joined, but the causal economic bridge between the external payment and reserved FXRP is missing.
- **Demo/scope:** FDC, FCC, Smart Account, nullifiers, and reserve accounting are too much for one day; the fallback explicitly fixtures the interrupted FAssets leg.
- **Nativeness:** the mistag problem is native, but the mechanism does not yet control the stranded asset.
- **Exact kill cause:** **uncollateralized/undefined link from mistagged XRP to the reserved FXRP being redirected, plus excessive integration breadth.**

### E2 — FixBond: KILL

- **Track primitives:** FCC can replay a private incident and FXRP can pay a named maintainer, but the claimed FAsset correction is delegated to another undefined retry/refund adapter.
- **Removal/joined path:** the payout is causally tied to a signed result, yet the worker can attest its own expected post-state unless the actual corrected protocol state is independently verified.
- **Demo/scope:** confidential patch execution, secret-safe sandboxing, deterministic replay, FDC/FAssets correction, post-state verification, and payout are far beyond one day. A fixture fault makes the product a demo harness.
- **Nativeness:** incident recovery is relevant, but the bounty/payment layer is secondary and generic.
- **Exact kill cause:** **self-referential private proof of fix, undefined real repair action, and infeasible secure patch-execution scope.**

### E3 — Veiled Exit: KILL

- **Track primitives:** real FXRP lock/redemption/refund and FCC private batch allocation are distinct and pass the removal tests.
- **Joined path:** strong if settlement capacity is an actual verified input, but “FDC-confirmed capacity” is not defined as a single supported fact; FDC verifies external events/transactions, not an aggregate exit-capacity metric without additional derivation.
- **Demo/scope:** commitments, encrypted batch handling, allocation root/proofs, claims, FDC derivation, and redemption reconciliation are too broad for the remaining day. Simulating the full external redemption leaves only an FXRP escrow allocation demo.
- **Nativeness/FCC honesty:** transparent exit urgency and scarce FAssets redemption are native; machine status is honest. Feasibility remains fatal.
- **Exact kill cause:** **undefined derivation of settlement capacity plus a multi-user proof/redemption surface too large for the remaining time.**

### E4 — Void Receipt: KILL

- **Track primitives:** FXRP payout/refund and FCC private inclusion are distinct; FDC would be load-bearing only if the chosen external event type and cancellation fact are actually supported.
- **Removal/joined path:** causality is coherent on paper, but “external event status” is left generic and may require unsupported Web2/custom truth rather than a concrete FDC attestation type.
- **Demo/scope:** the countdown, cancellation, and omission challenge fit 90 seconds; building the private round is feasible, but proving live FDC event resolution and FCC inclusion in one day is not. A fixture event removes the cross-system truth primitive.
- **Nativeness:** it is fundamentally a generic private prediction/outcome round and remains intact on any confidential-compute EVM chain.
- **Exact kill cause:** **unspecified FDC-attestable event, generic outcome-market core, and fixture-dependent Interoperable Asset proof.**

## Ranked architecture survivors

This is architecture rank only; no collision or prior-project evidence has been consulted.

1. **Mandate Zero** — smallest credible live proof and cleanest two-track removal tests.
2. **Quiet Exit Window** — strong execute/abstain experience; constrain “unwind” to one real FXRP action.
3. **Exit Envelope** — simple asset-recovery state machine; must avoid pretending a fixture route is a live yield venue.
4. **SplitLock** — best natural PMW/FCC composition, but highest chance of immediate operational failure.

## Mandatory next checkpoint before scoring

For each survivor, obtain a binary integration receipt before treating it as buildable:

- **Mandate Zero:** live Smart Account module accepts one FCC/FCE-signed cycle mandate and rejects a stale one.
- **Quiet Exit Window:** live Smart Account executes one capped FXRP action from an FCC/FCE-signed envelope.
- **Exit Envelope:** live FXRP deposit/unwind is controlled by an FCC/FCE-signed minimum-return envelope.
- **SplitLock:** live PMW submits one bounded XRPL transaction from an FCC/FCE-signed policy-intersection result.

If a receipt cannot be produced with the official/available interface, kill that survivor rather than replacing the track primitive with a mock.
